# D4 — PostgreSQL Database Architecture

**Status:** Complete — logical data model, ownership, integrity and recovery requirements documented  
**Date:** 2026-11-05  
**Depends on:** D1 stack; D2 frontend boundaries; D3 backend modules; C1–C15 content, assessment and review contracts  
**Baseline:** PostgreSQL; Prisma ORM 7 stable; one authoritative relational database  
**Scope:** Logical database architecture, not a deployed database or executable migration

## 1. Purpose and boundaries

D4 defines the logical data model, module ownership, entity relationships, key strategy, constraints, indexes, transaction/concurrency rules, migration governance, privacy classification and backup/recovery requirements.

It does not create a Prisma schema, SQL migration, database instance, seed data, production backup, restore job, hosting choice, identity provider, payment provider or retention schedule. D5 defines API contracts; D6 defines authentication; D7–D14 refine business-domain contracts; E/F/G stages define detailed security, testing, deployment and operational implementation.

PostgreSQL is the system of record. Browser/mobile clients never connect directly. Only the owning backend module accesses its tables through its repository.

## 2. Database architecture decisions

1. Use one PostgreSQL database for the initial modular monolith. Avoid premature database-per-service and distributed transactions.
2. Start with one physical PostgreSQL schema and explicit module-prefixed table names. Enforce logical ownership in NestJS module boundaries and repository architecture tests. Separate PostgreSQL schemas may be considered later if operational isolation justifies the migration.
3. Prisma ORM 7 stable is the typed access and migration baseline. Pin compatible versions when implementation begins.
4. Use UUID primary keys for internal entities. Public slugs/codes are separate unique alternate keys and never substitute for authorization.
5. Store timestamps as timezone-aware `timestamptz`, generated by the server/database in UTC. Keep locale/time-zone preference separate from event timestamps.
6. Normalize relationships and lifecycle state into relational columns/tables. Use JSONB only for bounded, versioned, runtime-validated content blocks or provider payload fragments that are not relational identity.
7. Enforce integrity with NOT NULL, UNIQUE, CHECK, foreign keys and transactions; application validation supplements, not replaces, database constraints.
8. Use immutable version rows for lessons, locale content, assessment definitions, review evidence and releases. Corrections create new versions or append events.
9. Do not hard-delete financial, approval, audit or learner progress history as a routine update. Retention/deletion workflows require approved policy and legal review.
10. No database credentials in clients, logs, repository files or seed fixtures. Production access uses least-privilege service credentials.

## 3. Logical ownership and PostgreSQL namespace

The initial database is a single database and schema; prefixes make ownership visible:

- `core_*`: stable shared reference/configuration records.
- `identity_*`: internal principal plus a separate provider-neutral external identity-link mapping; credentials/tokens remain outside ordinary application tables.
- `learner_*`: profile and preferences.
- `curriculum_*`: tracks, levels, modules, topics and prerequisites.
- `content_*`: canonical lessons, immutable versions, locale versions and structured blocks.
- `review_*`: submission, assignments, comments, defects, decisions, approvals and releases.
- `assessment_*`: assessment definitions, versioned items, attempts and responses.
- `progress_*`: enrolments and learner progress.
- `ai_*`: generation task/provenance and usage accounting metadata; no raw secrets.
- `asset_*`: object metadata and access ownership; bytes live in object storage, not PostgreSQL.
- `audit_*`: append-only security/business audit records.
- `platform_*`: idempotency and transactional outbox/inbox metadata where later contracts require it.

The full entity inventory and key relationships are in `D4_DATABASE_ENTITY_MATRIX.csv`. Names are logical proposals, not finalized Prisma model names.

## 4. Entity groups and relationships

### 4.1 Identity and learner

- `identity_principal` maps an internal UUID to an authenticated subject issued by the future identity boundary. Unique key: (issuer, subject). Do not store passwords or provider access tokens here.
- `learner_profile` is one-to-one with the principal; stores only necessary display/profile data and status.
- `learner_preference` stores selected locale (`te/en/ml/kn/ta/hi`), optional time zone and notification preferences. Locale must be one of the supported stable codes.
- Roles, permissions, sessions, MFA, recovery tokens and provider account linking are deliberately deferred to D6/E5. Avoid speculative auth tables.

### 4.2 Curriculum

- `curriculum_track` groups a learning pathway; `curriculum_level` defines ordered levels.
- `curriculum_module` belongs to a track/level; `curriculum_topic` stores stable topic identity and W3Schools source mapping.
- `curriculum_module_topic` maps modules to topics with an explicit ordering and uniqueness rule.
- `curriculum_prerequisite` records directed prerequisite edges between stable curriculum nodes. Reject self-edges and duplicate edges; application validation must reject cycles before publication.
- Slugs are unique within their parent scope. Published catalogue queries expose only approved active records.

### 4.3 Content and localization

- `content_lesson` is the stable logical lesson identity and canonical module association.
- `content_lesson_version` is immutable and numbered per lesson; includes content hash, outcome, lesson type, status, author and schema version.
- `content_locale_version` is immutable per lesson version and locale; unique (lesson_version_id, locale, version_number), with its own hash and review state.
- `content_block` stores ordered typed lesson blocks for a locale version. Structured fields remain relational where queried; bounded block payloads may use JSONB with a required schema_version and runtime validation.
- `content_source` maps versioned content to W3Schools URLs and topic IDs; source records do not imply permission to copy source text.
- `content_glossary_term` and `content_glossary_translation` hold stable term identity and locale-specific approved wording/version. Unreviewed translations remain drafts.
- `asset_object` stores metadata, owner, object key, MIME type, size, checksum, visibility and scan status. Object bytes remain outside PostgreSQL.

Six locale values are constrained to `te`, `en`, `ml`, `kn`, `ta`, `hi`. Code samples, identifiers and executable text are content payloads and must not be translated by database triggers.

### 4.4 Authoring, review and release

- `review_request` references an immutable lesson version, content hash, requested locale set and C15 state.
- `review_assignment` assigns a reviewer, role/capacity and locale; conflicts/recusal are explicit.
- `review_comment` and `review_defect` attach comments and severity to a version/hash and stable section/item reference.
- `review_decision` records the decision, reviewer, role, locale, gate outcomes, evidence references, reviewed hash and timestamp.
- `review_approval` records approval for a gate/locale/hash/policy version; uniqueness prevents duplicate active approval for the same tuple.
- `review_release` and `review_release_item` represent an immutable release manifest and its exact lesson/locale versions, hashes and approval references.
- State transitions are append-audited. A changed content/dependency hash invalidates affected approvals and makes the review stale. Database constraints enforce local invariants; C15 state-machine service validates allowed transitions.
- Author/reviewer separation and publisher authority are server-side authorization rules, not solely database checks.

### 4.5 Assessment and progress

- `assessment_definition` is a stable assessment identity; `assessment_version` is immutable and linked to a lesson/module.
- `assessment_item_version` stores a versioned question/item and schema-validated answer configuration. Answer keys are restricted to backend evaluation and reviewer roles.
- `assessment_attempt` records learner, version, start/submission timestamps, status and scoring-policy version.
- `assessment_response` stores per-item response data and evaluation result with uniqueness (attempt_id, item_version_id). Protect personal/free-text responses and never expose answer keys in learner queries.
- `progress_enrolment` links learner to a course/track where enrolment is required.
- `progress_record` stores a stable learner/content progress aggregate with status, completion evidence and concurrency version. Unique key prevents duplicate active progress for the same learner and content unit.
- `progress_event` is append-only evidence of started/completed/reset transitions. Repeated submissions use idempotency and transaction constraints. Progress is never trusted from client claims alone.

### 4.6 AI, platform reliability and audit

- `ai_generation_task` stores task state, owner, purpose, schema/rule version, input/output hashes, provider/model identifiers when available, usage/cost metadata and provenance references. Do not store secrets; raw prompts and full learner data require separate approved retention rules.
- `platform_idempotency` stores scoped idempotency key, request fingerprint, processing state and stable result reference. Unique (principal_scope, operation, key); write atomically with the business effect.
- `platform_outbox_event` stores schema-versioned event payload and delivery state in the same transaction as the originating business change when reliable asynchronous handoff is needed. `platform_inbox_receipt` records consumer/event deduplication and processing state. These are logical patterns; no queue product is selected.
- `audit_event` is append-only, with actor/service, action, timestamp, target IDs, before/after state references, reason, correlation ID and policy/version references. Never store credentials, full prompts or unrestricted payloads.
- Notification persistence, C13 project/submission persistence, and D12 billing entities remain in their domain-specific contract matrices and must be reconciled into one migration-ready schema inventory before implementation. D12's payment data contract matrix remains authoritative for proposed billing entities; D4 does not duplicate those definitions.

## 5. Key and relationship conventions

- Primary key: UUID, generated server-side using a cryptographically secure UUID implementation compatible with the selected PostgreSQL/Prisma versions.
- Foreign keys: explicit and non-null for mandatory ownership relationships. Optional references are nullable only when lifecycle semantics require it.
- Alternate keys: stable slug/code, source key, locale code or version tuple with scoped UNIQUE constraints.
- Version identity: immutable integer version number per parent plus content hash. Never overwrite a reviewed version in place.
- Ordering: explicit integer `position` with scoped uniqueness where order matters; do not infer order from UUID or insertion time.
- Time: `created_at`, `updated_at` only where mutable lifecycle requires them; event/decision timestamps are immutable. Use database/server UTC.
- Actor references: store internal principal/service IDs where known; preserve service identity for automation. Avoid copying display names into audit records as identity.
- JSONB: require `schema_version`, size limits, strict runtime validation and compatibility tests. Do not use JSONB for foreign keys, unique identity, authorization ownership or frequently filtered relational fields.

## 6. Integrity, constraints and concurrency

Mandatory constraint patterns:
- Unique external identity `(issuer, subject)` pair in `identity_external_link`; one profile per principal; locale enum/check constraint. `identity_principal` is the internal actor and must not store provider subject keys.
- Unique (parent_id, version_number) for immutable versions; unique lesson-version/locale tuple.
- Foreign keys with deliberate delete behavior. Prefer RESTRICT for historical/version/review/audit references; CASCADE only for disposable dependent data with an approved lifecycle.
- Check constraints for nonnegative counters/sizes, valid status values where stable, valid time ordering and bounded score ranges.
- Unique scoped positions for ordered curriculum and content blocks.
- Unique attempt/item response; unique active enrolment/progress identity; unique idempotency scope/key.
- Review approvals bind to content hash, locale, gate and policy version. Release item must reference the exact approved version.
- Prevent circular prerequisites in application-level graph validation; a simple foreign key cannot guarantee acyclicity.
- Use optimistic concurrency with a `version` integer for mutable aggregates; update with compare-and-swap semantics.
- Transactions are short and use-case scoped. Never hold a transaction open while calling AI, email, object storage, payment or sandbox providers.
- Retry only safe/idempotent operations. At-least-once async delivery is assumed; exactly-once execution is not promised.

## 7. Indexing and query policy

Create indexes from known access paths and validate with EXPLAIN/ANALYZE using representative, non-production test data. Initial candidate indexes:
- Curriculum: (track_id, level_id, position), module-topic lookup in both directions, prerequisite source and target IDs.
- Content: lesson/version parent and version number; locale version (locale, status, lesson_version_id); published retrieval keys; source topic mapping.
- Review: (state, submitted_at), assignments (reviewer_id, status, due_at), comments/defects by request/version, approval hash/gate/locale, release lookup by channel/status.
- Assessment: attempts (learner_id, submitted_at), responses by attempt and item.
- Progress: unique learner/content aggregate, learner/status/updated_at and content/status for reporting.
- AI: owner/status/created_at and task correlation.
- Audit: (occurred_at), (actor_id, occurred_at), (target_type, target_id, occurred_at), correlation ID.
- Idempotency/outbox: unique idempotency scope/key; pending outbox (status, available_at).
- Add indexes for foreign-key columns used in joins/deletes. Avoid indexing every column or duplicating unique indexes.
- Consider time partitioning for high-volume append-only audit/event tables only after measured volume and operational review; do not partition prematurely.

## 8. Transactions, migrations and release safety

- Prisma migrations are the sole normal schema-change path after implementation begins. No manual production DDL or schema push that bypasses reviewed migration history.
- Each migration includes intent, compatibility impact, expected lock/downtime behavior, data backfill plan, validation queries and rollback/forward-repair procedure.
- Prefer expand → migrate/backfill → verify → contract. Deploy code compatible with both old/new schema during rolling releases.
- Destructive changes require explicit approval, verified backup, restore rehearsal and a separate deployment window.
- Backfills are restartable, chunked, rate-limited and observable; do not run unbounded table rewrites during application startup.
- Migration tests run against an empty database and a representative previous-version snapshot. Validate constraints and query plans.
- Migration history and application release version are traceable. A rollback may require a forward-fix when data transformations are irreversible.

## 9. Privacy, data classification and retention

Initial classification:
- **Public:** published curriculum metadata and approved public lesson content.
- **Internal:** unpublished drafts, reviewer workflow metadata, operational configuration without secrets.
- **Confidential:** learner profile/preferences, progress, assessment responses, private project submissions, AI task metadata and private assets.
- **Restricted:** authentication/session secrets (owned by future identity provider boundary), payment credentials/provider secrets, recovery factors and security incident evidence. These must not be stored in ordinary application tables or logs.

Controls:
- Collect the minimum fields required for a learning feature.
- Separate public published content from private drafts and answer keys in repository/query authorization.
- Encrypt transport; require managed encryption at rest in the eventual hosting design. Key management/vendor is deferred.
- Define retention/deletion/anonymization schedules, legal holds, learner export and account deletion behavior before production; no retention duration is invented in D4.
- Backups inherit source-data classification and access restrictions. Backup copies must not become a loophole around deletion/retention policy.
- Avoid production personal data in local development, test fixtures, analytics and logs. Use synthetic data.
- Do not log assessment answers, source code, AI prompts, tokens or unnecessary personal fields.

## 10. Backup, restore and disaster recovery requirements

Production database operations must provide:
- Automated encrypted backups and point-in-time recovery where supported by the eventual PostgreSQL hosting/backup design.
- Separate access control and credentials for backup administration; backups stored separately from the primary failure domain.
- Defined retention, RPO and RTO approved from product/business requirements before launch; D4 deliberately does not invent numeric targets.
- Regular restore drills into an isolated environment, validating schema, row counts/integrity, application compatibility and access restrictions.
- Documented recovery sequence: declare incident; stop or fence writes; select recovery point; restore to isolated target; validate integrity and migration state; obtain approval; switch application connection; monitor; reconcile writes/events; record incident.
- Backup success alerts, failed-job alerts, restore-test evidence and immutable audit trail.
- Encryption key recovery tested alongside backup recovery. A backup that cannot be decrypted is not a usable backup.
- Object-storage assets and database metadata require coordinated recovery/versioning; a database restore must not reference permanently missing objects.
- No production backup or restore has been created or tested by this architecture task.

## 11. Security controls at the data layer

- Use separate database roles for migration, runtime application and read-only reporting; runtime role must not own schema or perform DDL.
- Restrict network access to database endpoints; TLS required for remote connections.
- Use parameterized queries/Prisma safe query APIs; prohibit string-concatenated SQL from untrusted input.
- Enforce row ownership and role authorization in application use cases. PostgreSQL row-level security may be evaluated in E-stage after tenancy/identity model is defined; not assumed enabled.
- Restrict answer-key, draft, review and audit queries to explicit service methods.
- Validate JSONB and uploaded metadata; do not deserialize arbitrary executable payloads.
- Audit privileged access and schema changes; redact secrets and sensitive values.
- Test backup access, migration privilege separation, injection resistance, cross-user isolation and unauthorized data export.

These are required future database implementation tests, **not executed by this specification**.

|---|---|---|
| D4-T01 | Insert duplicate principal issuer/subject | Unique constraint rejects |
| D4-T02 | Insert unsupported locale | Check/enum constraint rejects |
| D4-T03 | Create lesson version with duplicate version number | Unique constraint rejects |
| D4-T04 | Change content after review approval | New immutable version; old approval cannot authorize new hash |
| D4-T05 | Delete lesson referenced by a release | RESTRICT prevents destructive deletion |

| D4-T12 | Assessment response repeats same attempt/item | Unique constraint prevents duplicate |
| D4-T13 | Learner queries another learner's progress | Authorization denies access |
| D4-T14 | Learner query attempts to retrieve answer key | No answer-key field returned |
| D4-T15 | AI generation task returns malformed JSONB | Runtime schema validation rejects/quarantines |
| D4-T16 | Audit event update/delete attempted by runtime role | Database permissions deny mutation |
| D4-T17 | Runtime DB role attempts DDL | Permission denied |
| D4-T18 | Migration is incompatible with previous app version | CI migration compatibility gate fails |
| D4-T19 | Backfill restarts after interruption | Idempotent/chunked backfill resumes safely |

| D4-T22 | Database restored but asset object is missing | Cross-store integrity check identifies orphan reference |

D4 is accepted when entity ownership and relationships are explicit; key/constraint/index policies are documented; immutable content/review semantics are preserved; transaction/concurrency/idempotency rules are defined; migration, privacy, backup and restore requirements are recorded; and open policy/provider choices remain visible.
