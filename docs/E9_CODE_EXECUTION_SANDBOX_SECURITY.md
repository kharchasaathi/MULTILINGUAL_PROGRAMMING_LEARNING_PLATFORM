# E9 — Secure Code Execution Sandbox Architecture

**Status:** Complete at architecture, control catalogue and verification-design scope; implementation and enablement prohibited pending gates
**Date:** 2026-11-05
**Decision:** E-0010
**Authority:** D9 AI; D13 module communication; E1 threat model; E2 network zones; E3 application security; E6 database security; E7 API security; E8 AI prompt injection; L13–L15; E14; E15
**Scope boundary:** Provider-neutral design only. No sandbox runtime, VM/container, scheduler, image, network rule, quota, endpoint, compiler or test is implemented or validated.

## 1. Purpose and absolute enablement rule
Learner code is hostile by default, including code generated by AI or copied from lessons. Never execute it inside Next.js, NestJS, an AI adapter, a worker with application credentials, the database host or a shared control plane.

**Default state: execution disabled.** Future enablement requires implemented controls, independent E14 security evidence, L13–L15 curriculum/operational readiness and explicit E15 approval. This document does not authorize a pilot or production execution.

## 2. Threat model and security objectives
Protect the application/API, database, object storage, queues, identity, secrets, control plane, host kernel/hypervisor, other learners, tenants, provider networks, assessment integrity and platform availability. Assume arbitrary source, binaries, package manifests, filenames, compiler flags, stdin and test inputs; runtime/compiler/parser exploits; fork bombs; memory/disk/CPU exhaustion; malformed archives; network probing; side channels; concurrent abuse and attempts to escape the guest.

Every execution result and artifact is untrusted. A process exit code, stdout or timing is not proof of correctness, mastery or assessment outcome.

## 3. Trust boundaries and logical flow
Client → API authentication/authorization (E4/E5/E7) → execution broker → bounded queue/scheduler → disposable isolated runtime → bounded result collector/quarantine → owning module through D13 contract → authorized result API.

Broker and queue are not security boundaries by themselves. Enforce isolation at host/runtime, identity, network, storage and orchestration layers. The sandbox must not have direct database, queue, object-store or control-plane credentials.

## 4. Isolation and runtime requirements
- Place execution in dedicated E2 Z7, separate from application, data, workers and control plane. Deny routes to Z2/Z3/Z4/Z6 except a narrow result-ingress path through a hardened collector.
- Select isolation after a documented threat/cost/compatibility assessment. A hardened microVM or equivalent strong VM boundary is the preferred candidate for hostile multi-tenant execution; ordinary shared-kernel containers alone must not be presumed sufficient.
- If containers run inside a stronger boundary, use rootless execution, unique unprivileged UID/GID, read-only root filesystem, minimal capabilities, seccomp allowlist, mandatory access control, no-new-privileges and isolated namespaces.
- Never expose runtime/orchestration sockets, host devices, host PID/network namespaces, host paths, privileged mode, kernel modules or host administration interfaces.
- Create a fresh disposable instance and workspace per job; never reuse mutable process, memory, filesystem layer or credentials across runs. Destroy after bounded collection.
- Use minimal patched immutable runtime images pinned by digest. No package installation or image building with production credentials in the execution plane.
- Evaluate co-residency and side-channel risk; use dedicated hosts or stronger isolation where required by risk assessment.

## 5. Job contract and lifecycle
Create a server-owned versioned job envelope containing job ID, principal/tenant reference, authorized lesson/project/attempt reference, approved language/runtime profile, immutable image digest, source digest, bounded input references, CPU/wall-clock/memory/PID/disk/output limits, network profile (default none), expiry, idempotency key, policy version and trace ID.

Server-owned states: Requested → Authorized → Queued → Leased → Starting → Running → Collecting → Completed/Failed/TimedOut/Cancelled/Rejected → Destroyed. Reject invalid, expired, duplicate or out-of-order transitions. Client cannot choose image, command, host path, environment variables, limits, state or network profile.

- Authorize learner, project and entitlement before enqueue; re-check entitlement at worker claim and access before result delivery.
- Map language selection to a server-owned runtime catalogue. Use fixed entrypoint and argument templates; never interpolate untrusted input into a shell command.
- Pass source and stdin as bounded data, not as executable control-plane instructions.
- Apply queue quotas, fair scheduling, per-principal concurrency, bounded leases, idempotency, cancellation, deadline expiry and orphan reaping.
- Process exit success never directly changes assessment score, mastery, progress or entitlement.

## 6. Identity, secrets and privilege
- Run as non-root with unique ephemeral identity. No database, cloud, queue, registry, telemetry, provider or deployment credentials enter the sandbox.
- Do not expose cloud metadata, instance identity endpoints, environment secrets, SSH agents, signing keys or inherited parent environment.
- Use only a narrow, short-lived, job-bound result capability or broker-mediated channel. It permits bounded result upload to the collector and nothing else.
- Separate broker, scheduler, host agent, builder, signer, registry, collector and application identities. No sandbox process can call scheduler/control-plane APIs.
- Support independent revocation of execution credentials and immediate isolation of compromised workers.

## 7. Network isolation
- Default network is no network: no DNS, internet, LAN, private IP, loopback-to-host, peer job, database, cache, queue, object storage, API, metadata or control plane.
- Deny IPv4 and IPv6 routes from Z7 to Z2/Z3/Z4/Z6. Block raw sockets, tunnelling, alternate interfaces and DNS-over-HTTPS bypass.
- Enforce egress at host/hypervisor/network boundary, not only in guest configuration. Validate resolved IPs and redirects to prevent DNS rebinding and private-address access.
- Any future network-enabled lesson profile requires separate review, isolated egress proxy, destination allowlist, protocol/port limits, DNS/IP validation, response/time limits, no ambient credentials, no inbound connections and E15 approval.
- Result transfer is one-way and bounded through the collector; no arbitrary sandbox callbacks.

## 8. Resource exhaustion controls
Enforce externally: CPU quota and hard wall-clock deadline; memory/swap; PID/thread/process and file-descriptor limits; ephemeral disk/inodes; archive expansion; stdout/stderr and artifact byte/count caps; source/stdin/test-fixture limits; queue depth; per-user/tenant concurrency; fleet capacity and cost budgets. On breach, terminate the complete process tree and instance, record a typed reason, preserve only bounded diagnostics and reclaim resources. Learner code cannot raise its own limits.

## 9. Filesystem, source and artifact handling
- Provide fresh ephemeral workspace with only required source, runtime and approved harness. Mount runtime/root read-only.
- Hide host paths, home directories, sockets, devices, credentials and other job workspaces.
- Reject traversal, escaping symlinks, hardlink/device tricks, reserved names, deep paths and archive bombs.
- Treat binaries, generated files, logs and archives as untrusted. Quarantine; inspect MIME/content, size, expansion and malware before authorized download.
- Store under random object keys outside executable web roots with separate storage identity. Never execute returned artifacts in API, worker or CI.
- Escape terminal control sequences and output for the final rendering context; cap line and byte counts.

## 10. Supply chain and runtime integrity
- Build minimal immutable images with pinned dependencies, SBOM, provenance and signed attestations.
- Verify image signature, digest, provenance, policy and approved runtime profile before scheduling; reject mutable tags and unknown registries.
- Separate build, signing, promotion and runtime identities. Signing keys never enter build scripts or sandbox.
- Patch host kernel, hypervisor and language runtimes; retire unsupported/EOL versions.
- Prohibit arbitrary public package installation in production. If dependencies are necessary, use curated scanned immutable offline caches and allowlists.
- Stage image rollout with health checks, rollback and emergency digest revocation.

## 11. Assessment, output and privacy
- Keep hidden tests and answer keys outside learner process. Assessment authority remains C12 and owning backend.
- Do not reveal other learners' submissions, private tests, internal paths, hostnames, environment or scheduler details.
- Apply E11 purpose limitation, minimization, access, retention and deletion to source, inputs, outputs, artifacts and telemetry.
- Log job ID, pseudonymous principal reference, runtime digest, policy version, resource use and outcome; do not log secrets or unrestricted source by default.
- Re-authorize result and artifact downloads under E5; use short-lived object-specific links.

## 12. Monitoring and incident containment
Monitor escape indicators, unexpected syscalls, host/kernel anomalies, cross-job access, egress denials, metadata probes, resource breaches, queue abuse, image drift and signature failures. An independent kill switch must stop admission, pause queues, revoke profiles, terminate active instances, block egress, quarantine artifacts, revoke credentials and isolate compromised hosts. Rebuild from trusted images and reconcile affected jobs.

## 13. Verification and release gates
E14 must test runtime/kernel/hypervisor escape, namespaces/syscalls/devices, IPv4/IPv6/DNS/metadata/SSRF, cross-user and cross-tenant filesystem/process/memory/network isolation, resource exhaustion, queue abuse, archive/path attacks, image provenance, hidden-test confidentiality, replay/races/cancellation, cleanup, kill switch, revocation and recovery.

Production enablement requires approved threat assessment and isolation choice; E2 network deny evidence; E4/E5 workload identity and authorization; E6 storage isolation; E7 API quotas/contracts; signed image pipeline; monitoring and kill-switch drill; E11 privacy review; L13–L15 readiness; E14 independent test evidence; and explicit E15 approval. Any critical escape, cross-tenant leak, control-plane reachability or unbounded host impact blocks enablement.

## 14. Deferred decisions
Isolation primitive and host OS; cloud/region; supported languages and versions; runtime images; scheduler/queue; host fleet and tenancy; syscall/MAC profiles; network enforcement point; quotas and cost; dependency policy; artifact store/scanner; retention; patch SLOs; operator access and incident ownership. Resolve through measured prototype and recorded threat review before implementation.

## 15. Completion boundary
E9 completes architecture and future verification design only. **Code execution remains disabled.** No sandbox, container, microVM, scheduler, network rule, runtime image, resource limit, endpoint, scanner, monitor or test is claimed to exist. No in-process execution is permitted as a temporary workaround. Enablement requires L13–L15, E14 evidence and E15 approval.
