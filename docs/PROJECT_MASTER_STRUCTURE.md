## Development Rules
1. Blueprint before coding.
2. No module without approved requirements.
3. No feature without test cases.
4. No production release without quality gates.
5. Never expose secrets in frontend.
6. No untrusted code execution on main server.
7. Every module must have documented contracts.
8. Every change must be version controlled.
9. Root cause must be addressed, not hidden.
10. Update progress tracker after each milestone.
11. Never claim tests passed unless executed.
12. Preserve all approved project decisions.
13. Before starting each new content batch or switching to a second workstream, inspect relevant GitHub Actions runs and the previous batch's validation results. Read failure logs, classify the root cause, and apply necessary safe updates. Keep content work moving when a CI issue can be isolated and does not invalidate the current batch. Record unresolved technical issues as pending instead of silently ignoring them.
14. Keep S10 infrastructure items deferred until the final infrastructure phase unless the user explicitly changes priority.

## Workflow
PLAN -> DESIGN -> REVIEW -> IMPLEMENT -> TEST -> SECURITY CHECK -> APPROVE -> DOCUMENT -> NEXT TASK

### Batch-start operational check
Before each new batch:
1. Inspect the latest relevant GitHub Actions runs.
2. Verify the previous batch's required validation completed successfully.
3. If failed, inspect logs and identify the root cause.
4. Fix only issues relevant to the current work; isolate unrelated CI issues as tracked pending work.
5. Update the progress tracker and continue content work where safe.
